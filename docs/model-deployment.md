# 模型部署与服务器要求

版本：1.1 · 核验日期：2026-09-23 · 状态：部署设计与容量估算，未连接实际服务器、未做推理压测。

适用范围：[技术方案](technical-design.md)与[Spec](spec.md)的一期文本/对话翻译。Hy-MT2-7B 新增独立推理服务；Qwen 3.5 复用用户已有环境。本页不估算 Qwen 的新增 GPU，也不把微调硬件要求当作推理要求。

## 1. 模型角色

| 角色 | 一期模型 | 接入方式 |
| --- | --- | --- |
| translator | `tencent/Hy-MT2-7B`，先 BF16 | 独立私有模型端点，单片段纯文本输出，程序绑定片段 ID |
| reviewer | 已有 Qwen 3.5 | 对照原文、知识、候选输出结构化错误与覆盖列表 |
| repairer | 同一 Qwen 3.5 服务 | 有依据的局部修复，使用独立提示和调用记录，再完整审校 |
| conversation | 同一 Qwen 3.5 服务 | 意图、澄清、有依据的解释；不能绕过翻译内核 |

不假定现有 Qwen 是 9B、27B、35B-A3B 或其他型号，具体 model ID、量化、后端和空闲容量都需从用户环境登记。模型家族名称不能替代配置版本。

## 2. 已核实事实与显存推算

官方 Hy-MT2-7B 文件列表约 **16.1 GB**，配置为 BF16，32 层、8 个 KV heads、head_dim=128、`use_cla=false`，最大位置配置 262144 [D1][D2]。文件体积不是运行峰值显存，也不能用“7B×2 字节≈14 GB”替代实际权重检查。

按此配置、不量化 KV、无跨请求缓存共享，BF16 KV 的近似计算为：

`2(K,V) × 32(层) × 8(KV heads) × 128(head dim) × 2(bytes) = 131072 bytes/token = 128 KiB/token`

| 所有活跃请求的累计驻留 token（输入＋已生成输出） | 估算 KV 显存 |
| --- | --- |
| 4096 | 0.5 GiB |
| 8192 | 1 GiB |
| 16384 | 2 GiB |
| 4 条各 8192 | 4 GiB |
| 单条 262144 | 32 GiB |

此表为配置推导，不含权重、激活、CUDA Graph、框架、临时工作区和碎片，实际以后端分配为准。vLLM 可能预分配 KV 池，不能把 `nvidia-smi` 已预留显存当作所有请求都已使用。`max_model_len` 包含提示和输出 [D4]。**模型声明长窗口不代表一张 24 GB 卡能跑满长窗口**；一期按段落翻译，不将完整聊天历史发送给初译模型。

## 3. 服务器预算建议

下表是本项目的工程起步预算，**不是官方最低要求，也不是并发或 SLA 承诺**。GPU 要独占或有明确显存配额；24 GB 指卡的标称容量，实际以驱动可用值为准。

| 项目 | 现有资源起步档 | 新增资源建议档 |
| --- | --- | --- |
| Hy-MT GPU | 1 张支持 BF16、24 GB 显存的 NVIDIA GPU | 1 张支持 BF16、48 GB 显存的 NVIDIA GPU |
| 模型精度 | BF16，不量化，先建立质量基线 | BF16；多留 KV 与运行时余量 |
| CPU | 8 核/16 线程或 16 vCPU | 16 核或 32 vCPU |
| 主机内存 | 64 GB | 128 GB |
| NVMe | 至少 200 GB 可用空间 | 至少 500 GB 可用空间 |
| 初始上下文上限 | 8192 token（输入＋输出） | 同样从 8192 起步，再按真实需要增大 |
| 初始活跃序列 | 1；通过显存和时延验证后试 2 | 先 2，再逐档验证 4/8；不预先承诺吞吐 |
| 场景 | 研发、低并发试点，启动开销过大时减窗口或关闭 CUDA Graph 再核验 | 容量更宽裕的长期服务，适合增加并发/上下文 |

如果已有独占 24 GB 卡，可先验证，不必仅因 7B 标签购买多卡。新购设备时还要按实际 GPU 型号核对吞吐、散热、电源、机箱和机房要求；显存相同不意味着速度相同。**不建议把 16 GB GPU 作为本项目 BF16 标准部署档**。FP8/GGUF 等只作为后续容量实验，需兼容性检查及六方向质量回归，不能假定量化无损。

应用服务独立预算：API＋Worker＋小规模 PostgreSQL/Redis 试点可从 **8 vCPU、16–32 GB RAM、100 GB 可用 SSD** 开始，无需 GPU；生产数据库、备份及数据增长另计。也可先与 Hy-MT 同机，但需在上述 GPU 服务器资源外计入应用/数据库用量。现有 Qwen 服务须能被应用内网访问；不要求与 Hy-MT 同机，不默认迁移或重启它。单节点预算不包含高可用。

主机建议 Linux x86_64、Ubuntu 22.04/24.04 LTS；使用与锁定镜像匹配的 NVIDIA 驱动、CUDA/PyTorch 和 NVIDIA Container Toolkit。软件组合在 MODEL-01 兼容性验证后固定，不把通用 CUDA 版本写成所有 GPU 都适用的前提。网络至少稳定千兆内网；端口仅开放给应用/运维，模型认证由私有网关或服务实现。

磁盘余量用于权重、镜像/构建缓存、Tokenizer、日志和回滚版本；模型检查点需预先下载或离线导入。这里不包含文件翻译对象存储。

## 4. 推理服务初始配置

官方提供 vLLM / SGLang 的服务方式，当前示例包含从源码构建；不能推断任意旧版 vLLM 镜像支持该架构 [D3]。工程阶段须锁定验证过的后端版本或 commit、镜像 digest、模型 revision、Tokenizer 和 chat template。以下是待兼容性验证的**参数模板**，不是已经部署成功的脚本。

```bash
# /models/Hy-MT2-7B 必须是已下载、固定 revision 的完整本地检查点。
# 24 GB 独占 GPU 起步；端口只供受控内网调用。
vllm serve /models/Hy-MT2-7B \
  --served-model-name hy-mt2-7b \
  --dtype bfloat16 \
  --tensor-parallel-size 1 \
  --max-model-len 8192 \
  --max-num-seqs 1 \
  --gpu-memory-utilization 0.90 \
  --host 0.0.0.0 \
  --port 8001
```

如初始化内存不足，先核对独占显存和后端支持，再比较降低窗口、分批预填充和 `--enforce-eager` 的影响；不能靠无上限 CPU swap 隐藏不满足的容量。调整后的配置必须记录，不因启动成功就认定长输入/并发稳定。

请求侧初值采用官方 7B 建议：`temperature=0.7`、`top_p=0.6`、`top_k=20`、`repetition_penalty=1.05`、`max_tokens=4096` [D3]。这是待业务验证的基线，不能套用成 Qwen 的采样参数。8192 总预算下，输出预留最多 4096，其余用于目标原文、强制术语、上下文和模板；按实际 Tokenizer 计算，不够则语义分段，禁止截断原文。输出触顶视为未完成，不能直接发布。

Hy-MT 使用官方 chat template 和翻译任务格式；不强行套通用 JSON/tool-calling 模板。源语言/目标语言从平台代码映射到模板全称，背景与待译文本明确分开。术语、风格、背景支持须逐项验证，不能仅因有示例就视为已通过业务测试。

## 5. 现有 Qwen 3.5 接入登记

| 必填信息 | 用途 |
| --- | --- |
| base_url、实际 model ID、鉴权 Secret 引用 | 准确路由；密钥不写仓库 |
| 型号/权重 revision、量化/精度、Tokenizer/模板、推理后端版本 | 记录质量与复现边界；若只暴露别名则显式标记 |
| 实际 max context、max output、超时 | 防止原文/审校 JSON 截断；不能套用模型理论窗口 |
| JSON Schema/JSON mode、工具调用、stream 支持 | 实测能力；不支持工具调用时用结构化意图＋程序派发 |
| 思考模式的真实控制方式、reasoning 与 content 分离方式 | 分角色配置，不能把思考文本混入译文或 JSON |
| 可分配并发、RPM/TPM、与其他业务共享情况 | reviewer/repairer/conversation 使用一个端点级限流器 |
| 网络、身份、TLS、数据保留与日志策略 | 确保私有边界及审计 |

Qwen 官方示例区分本地兼容服务的 `chat_template_kwargs.enable_thinking` 和其他供应方接口字段；某些 Qwen 3.5 规格默认思考且不使用 `/think`、`/nothink` 软开关 [D5]。本项目不能仅修改提示词就假定模式已切换，须验证用户实际型号/后端，并记录生效配置。只对最终 `content` 做 Schema 校验；不得用不可靠字符串截断来吞掉异常结果。

试点从整个现有端点分配给本项目的 **2 个在途请求**预算开始验证；这是申请目标，获知实际配额前不可假定已有。审校和修复优先于普通解释，避免长对话占满审核容量。意图识别可先验证非思考模式，审校模式由六方向效果决定；若无法可靠关闭则预算中保留思考 token。所有角色独立超时、格式校验和失败记录，共享端点总量限制。

## 6. 部署验收记录

1. 固定上述软硬件版本和两端配置；运行真实六方向输入，验证术语、背景、输出截断及审校协议。
2. 以短句、多段技术文本和长上下文分别测量冷启动/热态显存，逐档增加请求；记录输入/输出 token、峰值显存、队列时间、TTFT、总耗时、吞吐、超时和 OOM。
3. 单独记录 Hy-MT、Qwen 各角色耗时及整个 Agent 的 P50/P95；整条链路吞吐受较慢阶段和共享 Qwen 配额限制，不能只报初译 tokens/s。
4. 验证 Qwen 失联、429、非法 JSON、Hy-MT 截断、Worker 重启、事件断线恢复，不允许“初译完成”伪装成最终成功。
5. 使用同一数据比较 Hy-MT 单模型、Qwen 单模型及双模型链路；部署可用与准确性达标分别出报告。未获得业务质量证据，只开放实验/人工试点。

本期不训练模型；未来 LoRA/全参训练需单独算资源。模型许可按实际固定 revision 的 LICENSE 审核，模型卡元数据不能代替许可文件。
